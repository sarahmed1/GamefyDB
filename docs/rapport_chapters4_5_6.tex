\section{Design Refinement}

During Sprint~0, the product backlog described eight output tables — four dimensions
and four fact tables. After inspecting the actual source data more carefully during
Sprint~1, the design was refined:

\begin{itemize}
  \item \textbf{Stock movements} were absorbed into \textit{dim\_item}. All stock
        records in the source file are outgoing sales — there are no restock entries.
        Because there is only one direction of movement, a dedicated fact table adds
        no analytical value; instead, quantity sold and total revenue are aggregated
        directly into the item dimension.

  \item \textbf{Member statistics} were kept as \textit{dim\_member}. The members
        file contains one summary row per member — cumulative totals, not individual
        events — so it naturally fits a dimension rather than a fact table.
\end{itemize}

The final schema therefore has six tables: four dimensions and two facts. This
simplification makes the Power~BI data model easier to navigate without losing any
of the required KPIs.

\section{Implementation of the Transformer Stage}

\subsection{Building the Dimension Tables}

\subsubsection{dim\_cashier}

The cashier dimension is built by collecting all distinct cashier names across the
three transactional domains — cash, sessions, and stock — sorting them alphabetically,
and assigning a sequential surrogate key starting at~1. The five cashier accounts
in the source data (\textit{guds}, \textit{monta}, \textit{taktek},
\textit{yassine}, \textit{youssef}) all appear in the result.

\subsubsection{dim\_terminal}

The terminal dimension is derived exclusively from the sessions file, since that is
the only source that records terminal names reliably. Each unique \texttt{(terminal,
terminal\_type)} pair becomes one row. The \texttt{terminal\_type} column is computed
during cleaning: terminals whose names contain \texttt{PS5} become \textit{PlayStation},
those containing \texttt{VIP} become \textit{VIP PC}, and all others become
\textit{Standard PC}. The final dimension contains 16 terminals.

\subsubsection{dim\_item}

The item dimension aggregates the stock table by item name, retaining the first
observed category, the median unit price, total quantity sold, and total revenue.
Median is used instead of mean for the unit price so that occasional data-entry errors
do not distort the representative price. The dimension contains 17 distinct items.

\subsubsection{dim\_member}

The member dimension is a direct copy of the cleaned members DataFrame with no
further aggregation. It contains 66 unique members, each described by their username,
first name, last name, cumulative session duration in minutes, and cumulative spend
in TND across usage, orders, USB data, and total.

\subsection{Building the Fact Tables}

\subsubsection{fact\_transaction}

The transaction fact table is built from the cash DataFrame. Each row represents one
cash register event — an income or expense entry recorded by a cashier. The foreign
key resolution works as follows:

\begin{itemize}[noitemsep]
  \item \textbf{cashier\_id} — looked up from the cashier name map built from
        \textit{dim\_cashier}.
  \item \textbf{terminal\_id} — assigned only for \textit{Computer Incomes} and
        \textit{Playstation Incomes} categories, since those are the only transaction
        types tied to a terminal. Rows in other categories carry a null terminal
        reference.
  \item \textbf{item\_id} — assigned only for \textit{Order Incomes} rows, by
        matching the transaction amount to the nearest item unit price in
        \textit{dim\_item}.
  \item \textbf{member\_id} — assigned only for \textit{Member Transactions} rows.
\end{itemize}

The table contains 3\,971 rows after cleaning.

\subsubsection{fact\_session}

The session fact table is built from the sessions DataFrame. Each row is one gaming
session opened at a terminal. The foreign key resolution is more straightforward here:
\texttt{cashier\_id} and \texttt{terminal\_id} are looked up directly by name, since
both columns are already clean strings after the cleaning stage. A \texttt{member\_id}
is assigned to rows whose \texttt{session\_type} is \textit{Member}.

The table retains all financial columns from the sessions source — \texttt{order\_transfer},
\texttt{usb\_data}, \texttt{usage}, \texttt{discount}, and \texttt{total} (all in TND)
— alongside \texttt{duration\_min} and \texttt{session\_type}.

The table contains 6\,285 rows after cleaning.

\section{Forecasting Technology}

\subsection{Prophet}

Three of the five forecasts use \textbf{Prophet}, a time-series forecasting library
developed by Meta. Prophet was chosen for the following reasons:

\begin{itemize}
  \item It handles irregular time series well — the café has no transactions on some
        days, and Prophet treats missing dates as gaps rather than zeros.
  \item It automatically detects weekly seasonality, which is the dominant pattern
        in a gaming center (busier on weekends).
  \item It produces an 80\% confidence interval (\texttt{yhat\_lower} and
        \texttt{yhat\_upper}) alongside the point forecast (\texttt{yhat}), giving
        the owner a range rather than a single number.
  \item It requires no manual parameter tuning for basic use cases.
\end{itemize}

Prophet fits a decomposable additive model of the form:
\[
  y(t) = \text{trend}(t) + \text{seasonality}(t) + \epsilon_t
\]
where the trend is a piecewise linear function and the seasonality is a Fourier-based
approximation of weekly and yearly patterns.

\subsection{SARIMA — Comparison Algorithm}

To objectively validate the choice of Prophet, a second algorithm was implemented in
parallel: \textbf{SARIMA} (Seasonal AutoRegressive Integrated Moving Average), the
classical standard for seasonal time series forecasting. SARIMA extends plain ARIMA
with an additional seasonal component, making it a fair comparison against Prophet
since both algorithms handle weekly seasonality.

SARIMA has six parameters: $p$, $d$, $q$ (non-seasonal) and $P$, $D$, $Q$ (seasonal),
plus a period $m$. Rather than tuning these manually — which is error-prone and
introduces human bias — the implementation uses \texttt{pmdarima}'s \texttt{auto\_arima}
function, which searches parameter combinations and selects the best by AIC
(Akaike Information Criterion). The seasonal period is set to $m=7$ for daily series
(capturing weekly patterns) and $m=4$ for weekly series (capturing monthly patterns
within the weekly aggregation).

\subsection{Evaluation Methodology — 80/20 Train/Test Split}

Both algorithms are evaluated using a chronological 80/20 split: the first 80\% of
the historical series trains the model, and the final 20\% is held out as the test
set. The model predicts the test period and the predictions are compared against the
real recorded values. The split is strictly chronological — a random split would allow
the model to train on future data to predict the past, which is unrealistic.

Three metrics are computed for each algorithm on each series:

\begin{itemize}[noitemsep]
  \item \textbf{MAE} (Mean Absolute Error) — average absolute difference in the same
        unit as the data (TND for revenue, integer count for members and sessions).
  \item \textbf{MAPE} (Mean Absolute Percentage Error) — average percentage error,
        scale-independent and comparable across series. A MAPE below 10\% is
        considered good, below 20\% acceptable, and above 20\% poor.
  \item \textbf{RMSE} (Root Mean Squared Error) — like MAE but penalises large
        individual errors more heavily. A large gap between RMSE and MAE signals
        the presence of outlier predictions.
\end{itemize}

The winner for each series is the algorithm with the lower MAPE. The results are
printed automatically at runtime and guide the recommendation of Prophet as the
primary forecasting algorithm.

\subsection{Aggregation Strategy}

A key implementation decision was the choice of granularity at which to fit Prophet.
For member transaction counts, fitting on daily data produced very low numbers (fewer
than five transactions per day) with many zero-days, which caused Prophet's confidence
interval to dip below zero. Aggregating to weekly totals before fitting solved this:
weekly counts are large enough for Prophet to estimate uncertainty reliably, and the
resulting \texttt{yhat\_lower} values stay non-negative. All member forecasts are
then clipped at zero and rounded to the nearest integer, since a member count cannot
be fractional.

\section{Implementation of the Five Forecasts}

\subsection{Revenue Forecast}

The revenue forecast filters the transaction table to income rows, sums the TND
amount by calendar day to produce a daily revenue series, and fits Prophet on that
series. Two horizons are produced from the same fitted model:

\begin{itemize}[noitemsep]
  \item \textbf{4-week weekly forecast}: 28 daily predictions aggregated into 4
        weekly buckets.
  \item \textbf{3-month monthly forecast}: 90 daily predictions aggregated into 3
        monthly buckets.
\end{itemize}

The output is saved to \texttt{output/forecasts/forecast\_revenue.csv} with columns
\texttt{date}, \texttt{granularity}, \texttt{yhat}, \texttt{yhat\_lower}, and
\texttt{yhat\_upper}.

\subsection{Member Activity Forecast}

The member forecast counts the number of member-type transactions per week, fits
Prophet on those weekly counts, and produces two horizons:

\begin{itemize}[noitemsep]
  \item \textbf{4-week weekly forecast}: four direct weekly predictions.
  \item \textbf{3-month monthly forecast}: 13 weekly predictions grouped into
        3 monthly buckets.
\end{itemize}

All values are clipped at zero and cast to integers before export.

\subsection{Peak Hours Analysis}

The peak hours analysis does not use Prophet — it is a descriptive summary of
historical patterns, not a time-series forecast. It computes two views from the
transaction history:

\begin{itemize}
  \item \textbf{By hour of day}: the average number of transactions recorded per
        hour, across all days in the dataset. This reveals at which times of day
        the center is most active.
  \item \textbf{By day of week}: the average number of transactions per day of the
        week. This shows the weekly rhythm — typically Saturday and Sunday for a
        gaming center.
\end{itemize}

Each view also includes a \texttt{pct\_of\_total} column: the share of each period's
average relative to the sum for that period type. The two views are saved as separate
files — \texttt{peak\_hours\_by\_hour.csv} and \texttt{peak\_hours\_by\_day.csv} —
to avoid the scale inconsistency that would arise from mixing hourly and daily figures
in a single table.

\subsection{Session Volume Forecast}

The session volume forecast uses the daily transaction count as a proxy for activity
volume, since the sessions table has no timestamps that could be used directly. The
approach is the same as for revenue: Prophet is fitted on the daily counts, producing
4-week and 3-month horizons. The output is integer-valued and clipped at zero.

\subsection{Stock Replenishment}

The stock replenishment module takes a different approach from the Prophet-based
forecasts: rather than projecting a time series forward, it analyses historical
consumption rates to produce a purchasing recommendation for each item.

The calculation has three steps:

\begin{enumerate}
  \item \textbf{Average weekly consumption}: total units sold divided by the number
        of weeks covered by the dataset. A minimum of one week is enforced to avoid
        division by zero on sparse data.
  \item \textbf{Suggested order quantity}: the average weekly consumption multiplied
        by a configurable safety factor (default~1.5). This provides a buffer above
        the typical weekly demand, accounting for variation. The result is rounded
        up to the nearest integer so partial units are never suggested.
  \item \textbf{Reorder frequency}: items averaging 20 or more units per week are
        classified as \textit{weekly} restocks; 8–20 as \textit{bi-weekly}; and
        below~8 as \textit{monthly}.
\end{enumerate}

\section{Member Segmentation}

\subsection{Objective}

Beyond forecasting, Sprint~4 adds a customer intelligence capability: grouping the
66 members into behaviorally distinct segments using unsupervised machine learning.
The goal is to give the owner an objective, data-driven answer to the question
\textit{which customers are most valuable?}, enabling targeted promotions and
retention efforts.

\subsection{Algorithm — K-Means Clustering}

K-means is an unsupervised clustering algorithm that partitions data into $k$ groups
by minimising the within-cluster sum of squared distances from each point to its
cluster centroid. It was chosen over alternatives (DBSCAN, hierarchical clustering,
RFM scoring) for three reasons: it is interpretable, well-known in academic literature,
and produces a fixed number of segments that map directly to business labels.

The number of clusters is fixed at $k=4$. This was chosen to produce four segments
that cover the natural range of member behaviour without over-fragmenting a dataset
of 66 members.

\subsection{Features}

Three features were selected from \textit{dim\_member}:

\begin{itemize}[noitemsep]
  \item \textbf{\texttt{total\_tnd}} — total money spent at the center.
  \item \textbf{\texttt{duration\_min}} — total time spent (cumulative session minutes).
  \item \textbf{\texttt{orders\_tnd}} — money spent on food and drink orders.
\end{itemize}

The \texttt{usb\_tnd} column was excluded because it is always zero. The
\texttt{usage\_tnd} column was excluded because it is highly correlated with
\texttt{total\_tnd} and would give disproportionate weight to the spend dimension.

Before clustering, all three features are normalised using \textbf{StandardScaler}
(zero mean, unit variance). This step is mandatory for K-means: because the algorithm
measures Euclidean distance, features with larger numerical ranges would otherwise
dominate the clustering regardless of their actual importance.

\subsection{Segment Labels}

After fitting, the four cluster centroids are inspected and labelled automatically
using the following heuristic:

\begin{enumerate}
  \item The cluster with the highest centroid \texttt{total\_tnd} is labelled
        \textbf{Heavy Users}.
  \item The cluster with the lowest centroid \texttt{total\_tnd} is labelled
        \textbf{Light Users}.
  \item Of the two remaining clusters, the one with the higher ratio of
        \texttt{orders\_tnd} to \texttt{duration\_min} is labelled
        \textbf{Casual Spenders} (they spend relatively more on food than on time).
  \item The final cluster is labelled \textbf{Regulars}.
\end{enumerate}

\subsection{Cluster Quality — Silhouette Score}

Because K-means is unsupervised, there is no ground-truth label to compare against.
Cluster quality is instead measured by the \textbf{silhouette score}, which quantifies
how well each point fits its own cluster relative to the nearest other cluster.
The score ranges from $-1$ to $1$: values above $0.5$ indicate well-separated clusters,
$0.25$--$0.5$ indicate reasonable structure, and below $0.25$ indicate overlapping or
poorly defined clusters. The silhouette score for the current dataset is reported at
runtime.

\chapter*{General Conclusion}
\addcontentsline{toc}{chapter}{General Conclusion}

This project set out to answer a practical question: how can the raw, artefact-laden
Excel exports of a gaming center be turned into a clean, reliable dataset that
supports real decision-making? The answer, delivered through four iterative sprints,
is the GamefyDB system.

Sprint~0 established the foundations: a clear requirements specification, a Scrum
team, a product backlog, and a dimensional model based on the Kimball approach. The
decision to use a star schema over a snowflake or galaxy model proved correct — the
resulting six-table structure is simple enough for Power~BI to navigate without joins,
yet complete enough to answer all the KPIs defined with the Product Owner.

Sprint~1 tackled the hardest part of the project: the source data. The four
\texttt{.xls} files were more problematic than anticipated — page-break artefacts,
encoding errors, non-standard number formats, merged cells that shifted column
positions, and a footer row that masqueraded as a data row. The solutions developed
during this sprint (\texttt{xlrd}-based reading, empirical column maps, artefact
stripping, the \texttt{u202f} thousands-separator fix) are all documented and
maintainable. A new export from the management software with the same format can
be processed without any code changes.

Sprint~2 produced the star schema itself. The design was refined during
implementation: the stock movements table was absorbed into \textit{dim\_item} when
it became clear that all movements were sales, and the member statistics table was
kept as a dimension because it already contains one aggregated row per member. The
final six-table schema — four dimensions and two fact tables — is clean, correctly
keyed, and exports in a single command.

Sprint~3 delivered the Power~BI report. Four dashboard pages — Revenue Overview,
Rankings, Live Ops, and Shift Report — cover the full range of operational questions
the owner faces daily. All measures were validated against the source data, and the
template file (\texttt{SalesDashboard.pbit}) means the report can be refreshed with
a new pipeline run in minutes.

Sprint~4 extended the system into predictive and analytical territory. Three
complementary machine-learning techniques were implemented and evaluated. First,
\textbf{Prophet-based forecasting} produces revenue, member activity, and session
volume projections for horizons of four weeks and three months, giving the owner a
concrete planning window. Second, a \textbf{SARIMA comparison} was run alongside
Prophet on an 80/20 chronological train/test split to objectively justify the
algorithm choice: both models were evaluated on MAE, MAPE, and RMSE, and the winner
per series was identified automatically. Third, \textbf{K-means member segmentation}
groups the 66 members into four behaviorally distinct segments — Heavy Users, Casual
Spenders, Regulars, and Light Users — enabling targeted promotions based on actual
spending and visit behaviour rather than intuition.

The peak-hours analysis identifies the optimal staffing windows. The stock
replenishment module provides actionable reorder recommendations that match the
purchasing frequency the owner was already using informally for the fastest-moving
items — confirming that the data-driven result aligns with operational experience.

Several directions remain open for future work. The current pipeline reads static
Excel files; connecting it to the management software's live database would enable
automatic daily refreshes. The Prophet models could be re-evaluated as more historical
data accumulates — the current dataset covers fewer than eight months, which limits
seasonality detection. A dedicated web application could expose the forecasts and
dashboards to staff without requiring access to Power~BI Desktop. The member
segmentation could be extended with a temporal dimension once per-visit timestamps
become available, enabling true RFM (Recency, Frequency, Monetary) analysis.

Overall, GamefyDB demonstrates that even a small business operating on spreadsheets
can gain genuine analytical capability through a well-designed ETL pipeline and a
modest investment in tooling. The center now has a repeatable, automated process that
transforms its operational data into a resource for decision-making — something that
was entirely absent at the start of the internship.
